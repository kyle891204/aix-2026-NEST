# 개발 규칙

## 개발 원칙과 첫 작업

- 기능별 담당자 1명, 완료 조건, 선행 작업을 이슈에 적는다.
- React: 기능 안에 화면·컴포넌트·훅·API를 묶고 공통 HTTP 코드는 `shared/api`를 사용한다.
- 화면에서 직접 fetch하지 않고 `shared/api/client.ts`를 통해 요청한다. 아직 없는 API는 구현 완료처럼 표시하지 않는다.
- Java: 기능별 패키지 안에서 controller → service → repository/외부 연동 책임을 나눈다.
- API·DB 변경은 관련 문서와 예시도 함께 수정한다.
- 기능 문서는 `docs/features/`에 두고 이름은 관련 코드 폴더 이름을 기준으로 정한다. 같은 기능의 문서가 있으면 그 문서를 고친다.
- 상세 설명은 한 문서(API는 `api.md`, 배포 설정은 `deployment.md`)에서 관리하고 다른 곳에는 요약과 링크를 둔다. 상세를 고치면 요약도 맞춘다.
- 문서 위쪽에는 현재 동작을, 아래쪽에는 날짜를 붙인 검증·결정 기록을 둔다.
- "미구현", "비활성", "아직" 같은 상태 설명은 관련 코드·설정으로 확인한다.
- 문서를 만들거나 옮기거나 합치거나 지우면 관련 링크와 README 문서 표를 고쳐, 이전 경로로 찾던 사람도 새 문서를 찾을 수 있게 한다.
- 위 문서 규칙은 새로 쓰거나 고치는 절부터 적용한다. 기존 문서 전체를 한 번에 맞추지 않는다.
- AI 결과에 날짜·서류·대상을 임의로 추가하지 않는다. 원문과 번역·분석 상태를 분리한다.
- 번역 실패 시 원문과 실패 안내를 제공한다. 중요한 공지를 불확실한 판별로 숨기지 않는다.
- 키·토큰·실제 사용자 공지는 Git과 브라우저 공개 환경변수에 넣지 않는다.
- 고정 UI 번역과 공지/게시글 AI 번역은 별도 방식으로 구현한다.
- DB를 확정하면 JPA·드라이버·마이그레이션을 함께 추가한다. 지금은 DB 없이 기동 가능하도록 했다.
- 학사일정·개인 일정은 구현했다([schedule](features/schedule.md)). 개인 일정은 아직 서버가 아닌 브라우저에 저장한다.
- AI 도구 사용 기록은 기존 저장소의 `PROMPTS.md` 규칙을 따른다.

## 브랜치 운영 규칙

### 1. 기본 원칙

- 기능별 작업 브랜치를 생성하여 개발한다.
- 변경 사항은 Pull Request(PR)를 통해 main에 병합한다.
- PR은 다른 팀원 1명의 검토를 거친다.
- main은 실행 가능한 상태로 유지한다.

### 2. 브랜치 구성

| 브랜치 | 역할 |
| --- | --- |
| main | 검토가 완료된 코드와 운영 배포의 기준 브랜치 |
| feat/* | 새로운 기능 개발 |
| fix/* | 오류 수정 |
| docs/* | 문서 작성 및 수정 |
| develop | 초기 개발 과정에서 사용한 통합 브랜치 |

최근 개발은 작업 브랜치에서 main으로 PR을 보내는 방식으로 진행한다.
develop을 거치는 방식은 현재의 기본 작업 흐름으로 사용하지 않는다.

### 3. 브랜치 이름

작업 종류와 내용을 알 수 있도록 이름을 작성한다.

- 기능 개발: feat/기능명
- 오류 수정: fix/수정내용
- 문서 작업: docs/문서내용

예시:
- feat/personal-schedule-save
- fix/school-notice-fetch
- docs/branch-rules

하나의 브랜치에는 하나의 작업 목적을 담는다.

### 4. 작업 절차

1. 최신 main을 기준으로 작업 브랜치를 생성한다.
2. 작업 내용을 구현하고 변경 범위에 맞는 테스트와 빌드를 확인한다.
3. 작업 브랜치를 원격 저장소에 push한다.
4. main을 대상으로 PR을 생성한다.
5. 다른 팀원 1명이 검토하고, 필요한 수정 사항을 반영한다.
6. 충돌과 검증 결과를 확인한 뒤 main에 병합한다.

선행 기능이 아직 병합되지 않아 다른 작업 브랜치를 기준으로 개발하는 경우,
PR에 의존 관계와 병합 순서를 명시한다.

### 5. PR 작성

저장소의 PR 템플릿을 사용하여 다음 내용을 작성한다.

- Summary: 변경 사항 요약
- Description: 구체적인 작업 내용
- Related Issues: 관련 이슈
- Screenshots / Videos: 화면 변경이 있는 경우 참고 자료
- Notes to Reviewers: 검토 시 참고할 내용과 검증 결과

완료한 검증과 아직 확인하지 못한 내용을 구분하여 기록한다.

### 6. GitHub 보호 설정 현황

확인일: 2026-11-17

main을 대상으로 하는 `protect main branch` 규칙이 존재하지만,
현재 비활성화되어 있다.

해당 규칙에 저장된 내용은 다음과 같다.

| 항목 | 저장된 설정 |
| --- | --- |
| 적용 대상 | main |
| 브랜치 삭제 제한 | 포함 |
| 강제 push 제한 | 포함 |
| PR을 통한 병합 | 포함 |
| 필수 리뷰 승인 수 | 0명 |
| 새 커밋 push 시 기존 승인 무효화 | 포함 |
| 코드 소유자 리뷰 필수 | 미설정 |
| 리뷰 대화 해결 필수 | 미설정 |
| 필수 상태 검사 | 규칙에 포함되지 않음 |

위 항목은 비활성 규칙에 저장된 설정이며 현재 강제되지 않는다.
팀의 ‘다른 팀원 1명 검토’ 원칙은 별도로 준수한다.

저장소에서는 Merge commit, Squash, Rebase 병합을 모두 허용하며,
병합 후 작업 브랜치 자동 삭제는 설정되어 있지 않다.
